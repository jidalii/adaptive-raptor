# 候选数据集评估：SQuAD、Natural Questions、TriviaQA、MuSiQue、HotpotQA、2WikiMultiHopQA

> 状态：调研笔记，2026-11-11。没有下载数据，也没有运行任何 API。
> 数据集的规模数字大多凭记忆，标了"≈"。写进论文之前要和原始论文或数据集主页逐项核对。
> 这份笔记不修改研究计划书。要不要采用这里的任何数据集，由团队决定。

## 0. 背景：为什么要评估这些数据集

QASPER 上的结论是：
- 逐题 oracle 的 headroom 真实存在，在 1000 token 时约 +12 F1，pilot 重跑后约 75% 仍然成立；
- 但这个 headroom 无法从 LLM 画像、问题特征或检索特征中预测出来；
- 见 `NOTES.md` 和 `docs/OPTIMIZER_FLOW.md`。

接下来想回答两个问题：
1. **idea.md 里"按粒度选层"的设想**：需要层级真正有意义的长文档。QASPER 的树只有 1–2 层摘要。
2. **"不可预测"是不是 QASPER 特有的？** 需要一个前人已经报告过"路由有效"的设置，作为正对照。

本文列出的 6 个数据集，正好就是 Adaptive-RAG（Jeong et al., NAACL 2024）使用的基准：
- 单跳：SQuAD、Natural Questions、TriviaQA；
- 多跳：MuSiQue、HotpotQA、2WikiMultiHopQA。

Adaptive-RAG 的做法是：每个数据集抽 500 道题评测，沿用 IRCoT（Trivedi et al.）的设置；用 T5-Large 分类器把问题分到三类：A（不检索）、B（单步检索）、C（多步检索）。

## 1. 评估维度

| 维度 | 为什么重要 |
|---|---|
| **D1 文档长度与层级意义** | RAPTOR 树要有多层，而且各层要有"细节 → 概括"的含义，idea.md 才有东西可选 |
| **D2 答案格式和指标** | 短答案或片段可以直接沿用 QASPER 风格的 token-F1，自由文本则要换指标 |
| **D3 证据标注** | 有金标证据，才能离线测检索召回，像压缩实验那样不花钱 |
| **D4 复杂度金标** | 有跳数或题型标注，可以直接检验画像器的"复杂度判断"准不准，不必等生成结果 |
| **D5 污染与记忆** | Wikipedia 上的事实类题目，LLM 闭卷也能答对，会稀释检索带来的效果 |
| **D6 新意** | 已经被路由类工作充分研究过的设置，再做一遍能提供的新信息有限 |
| **D7 成本** | 按 DeepSeek 非高峰价和 QASPER 实测单价估算，见第 4 节 |

## 2. 逐个数据集

### 2.1 SQuAD（v1.1 / v2.0）
- **内容**：众包标注者看着一段 Wikipedia 段落提问，答案是该段中的片段。
  - v1.1 约 10 万题（train ≈ 87.6k，dev ≈ 10.6k），来自约 536 篇文章；
  - v2.0 另加约 5 万道不可回答题（train ≈ 130k，dev ≈ 11.9k）；
  - 开放域版本（SQuAD-open，DrQA 设置）在整个 Wikipedia 上检索。
- **指标**：EM / F1，和 QASPER 的抽取式 F1 一致。
- **对本项目**
  - D1 差：原始设置的上下文只有一段，约 150 token，不需要检索。按文章建树，一篇文章约 40–50 段，可以建 1 层摘要，规模比 QASPER 小。
  - D3 好：答案片段所在的段落就是金标证据。
  - D4 无。
  - D5 高。另外，标注者是看着段落提问的，问题和原文词汇重叠很高，BM25 已经很强，检索几乎不是瓶颈。
- **结论：不适合作为主实验。** 最多作为"单跳、检索容易"的对照组。

### 2.2 Natural Questions（NQ）
- **内容**：真实的 Google 搜索查询，配上一个完整的 Wikipedia 页面，标注了长答案（段落）和短答案（片段）。
  - train ≈ 307k，dev ≈ 7.8k，test ≈ 7.8k（test 不公开）；
  - 原始数据有几十 GB；
  - 开放域版本 NQ-open（约 79k / 8.8k / 3.6k）只保留 ≤5 个 token 的短答案，在 DPR 的约 2,100 万段 Wikipedia 上检索。
- **指标**：短答案 EM / F1，可以直接沿用。
- **对本项目**
  - D1 中等：每题对应一整页 Wikipedia，经常有几千 token，和 QASPER 的单篇论文相当。树大概也是 1–2 层，层级意义一般。
  - D3 好：长答案就是金标段落，可以离线测检索召回。
  - D4 无：全部是单跳题。
  - D5 高。
  - 优点：查询是真实用户写的，不是看着原文出的题，检索更有难度，比 SQuAD 更真实。
- **结论：部分适合。** "单文档、整页检索"的设置和 QASPER 同构，可以用来检验 QASPER 的结论能否推广到另一个领域。但它无法验证"按粒度选层"。

### 2.3 TriviaQA
- **内容**：问答爱好者写的知识竞赛题，事后再用远程监督配上证据文档（Wikipedia 和网页）。约 9.5 万个问答对，约 65 万篇证据文档；有 Wikipedia 和 Web 两个子集，以及人工核验过的子集。
- **指标**：EM / F1，带答案别名表，可以沿用。
- **对本项目**
  - D1 中等偏好：证据文档往往很长，但每题可能对应多篇文档。
  - D3 弱：证据是靠"文档里出现答案字符串"自动配上的，不能保证文档里真有推理依据。
  - D4 无。
  - D5 **最高**：知识竞赛题是 LLM 背得最熟的一类，闭卷正确率很高，检索的作用会被严重稀释。
- **结论：不太适合。** 污染问题会让"检索配置怎么选"这个变量的作用接近 0。

### 2.4 MuSiQue
- **内容**：把多个单跳问题组合成 2–4 跳问题，并专门过滤掉可以走捷径的题。
  - MuSiQue-Ans 约 2.5 万题（train ≈ 19.9k，dev ≈ 2.4k，test ≈ 2.5k）；
  - 每题给 20 段文字（金标段落加干扰段落）；
  - MuSiQue-Full 还配有不可回答的对照题。
- **指标**：答案 F1，加上支持段落 F1。
- **对本项目**
  - D1 差：20 段约 2–3k token，段落彼此独立，层级没有粒度含义。
  - D3 好：标注了支持段落。
  - D4 **最好**：每题都有跳数（2 / 3 / 4）和分解后的子问题，可以直接检验画像器的"需要几条信息"和"是否需要联合推理"判断得对不对。这正是 QASPER 上 H1 方向相反的那部分。
  - D5 中等：组合题不容易直接背出来，比其他 5 个数据集都低。
  - D6 低：Adaptive-RAG 和 IRCoT 都用过。
- **结论：最适合做"复杂度画像能不能预测收益"的正对照。** 不适合验证层级。

### 2.5 HotpotQA
- **内容**：基于 Wikipedia 的多跳问答，题型分为 bridge 和 comparison，并标注了支持句。
  - train ≈ 90.4k，dev ≈ 7.4k（test 不公开）；
  - distractor 设置：每题 10 段，合计约 1–1.5k token；
  - fullwiki 设置：约 520 万条 Wikipedia 摘要段。
- **指标**：EM / F1（片段或 yes/no），可以沿用。
- **对本项目**
  - D1 差：distractor 设置下 leaf@2000 就能放下全部内容。fullwiki 的段落彼此独立，在上面建树要花约 $150–250，还要几天计算。
  - D3 好：句子级的支持事实。
  - D4 中等：有题型（bridge / comparison），但已有研究指出很多题用单跳就能答对。
  - D5 高。
  - D6 低。
- **结论：部分适合，用作复杂度路由的对照。** 推荐的做法是"混合语料"：把约 1,000 道题的全部段落合成一个约 1 万段的语料库，建一棵共享树。这样干扰段来自别的问题，检索才有意义，费用约 $3–4。

### 2.6 2WikiMultiHopQA
- **内容**：用 Wikipedia 加上 Wikidata 的模板生成多跳题，题型有 comparison、inference、compositional、bridge-comparison 四种，标注了证据三元组。
  - train ≈ 167k，dev ≈ 12.6k，test ≈ 12.6k；
  - 每题 10 段文字。
- **指标**：EM / F1，可以沿用。
- **对本项目**
  - D1 差。
  - D3 好：证据三元组加上支持段落。
  - D4 有，但**题型几乎可以从问题模板直接看出来**。路由器在这里会显得很准，但那是模板痕迹，推广不到别的数据集。
  - D5 中等偏高。
- **结论：不太适合作为主要证据。** 如果用，要和 MuSiQue 一起报告，并说明模板问题。

## 3. 汇总

| 数据集 | D1 层级 | D2 指标 | D3 证据 | D4 复杂度金标 | D5 污染 | 验证"按粒度选层" | 验证"复杂度可预测" |
|---|---|---|---|---|---|---|---|
| SQuAD | ✗ | ✓ | ✓ | ✗ | 高 | ✗ | ✗ |
| Natural Questions | △ | ✓ | ✓ | ✗ | 高 | ✗（可以做 QASPER 结论的推广检验） | ✗ |
| TriviaQA | △ | ✓ | △ | ✗ | 最高 | ✗ | ✗ |
| MuSiQue | ✗ | ✓ | ✓ | **✓ 跳数** | 中 | ✗ | **✓ 首选** |
| HotpotQA | ✗ | ✓ | ✓ | △ 题型 | 高 | ✗ | ✓ 次选 |
| 2WikiMultiHopQA | ✗ | ✓ | ✓ | △ 模板题型 | 中高 | ✗ | △ |
| *对照：NarrativeQA* | ✓（约 3 层） | ✗ 要换 ROUGE-L | △ | ✗ | 中 | **✓** | ✗ |
| *对照：QASPER（现有）* | △（1–2 层） | ✓ | ✓ | △ 答案类型 | 低 | △ | 已证明不可预测 |

（✓ = 好，△ = 部分满足，✗ = 不满足）

**要点：这 6 个数据集都不能用来验证 idea.md 的"按粒度选层"。** 它们要么上下文太短，要么段落彼此独立，RAPTOR 的层级在上面没有粒度含义。要验证这一点，应该选 NarrativeQA 或 QuALITY（RAPTOR 原文用的就是这两个）。

## 4. 成本估算（非高峰，粗略）

单价沿用 QASPER dev 的实测值：
- 建索引：每 100 万叶子 token 约 $0.47–0.81；
- 生成：每题每配置约 $0.00024，按 10 种配置、平均约 1,500 token 上下文计。

| 方案 | 规模 | 建索引 | 生成 | 合计 |
|---|---|---|---|---|
| MuSiQue，抽 500 道 dev 题，混合语料（约 1 万段） | 约 100 万 token | 约 $0.5–0.8 | 约 $1.2 | **约 $2** |
| HotpotQA，抽 1,000 道 dev 题，混合语料 | 约 120 万 token | 约 $0.6–1 | 约 $2.4 | **约 $3–4** |
| Adaptive-RAG 风格，6 个数据集各 500 题（按题或按文章建小树） | 约 600 万 token | 约 $3–5 | 约 $7 | **约 $10–12** |
| 再加 train 标签，用来拟合预测器（每个数据集再抽 500 题） | 同上 | 同上 | 同上 | 再加约 $10–12 |
| HotpotQA fullwiki，或在 NQ / TriviaQA 的全量 Wikipedia 上建树 | 几亿 token | $150 以上 | — | 不建议 |

另外的工作量：每个数据集要写一个加载器，转换成 `documents.jsonl` 和 `questions.jsonl`；单跳数据集要处理答案别名；画像 prompt 中的数据库元数据也要改。总计约 1–2 天，主要是写代码，不花钱。

## 5. 建议

1. **不要用这 6 个数据集去验证"按粒度选层"。** 如果要验证，换 NarrativeQA，见之前的成本评估。
2. **如果要回答"不可预测是不是 QASPER 特有的"，首选 MuSiQue。**
   - 先做一个免费的检查：在 MuSiQue dev 上运行冻结的 `profile_v3` 画像器（只看问题，每题约 173 token，500 题约 $0.01–0.02，需要批准）。把它的"需要几条信息"和"是否需要联合推理"判断与金标跳数对比。这可以把"画像器判断不准"和"判断准了但没用"区分开。
   - 然后再跑约 $2 的配置网格，看 oracle headroom 和收益能不能预测。
3. **要注意数据集身份带来的混淆。** Adaptive-RAG 的分类器在 6 个数据集混合的测试集上表现好，有一部分原因是：单跳和多跳数据集本身就对应不同的最优动作，而判断"这题来自哪个数据集"很容易。如果我们也用混合测试集，**必须分开报告"同一数据集内部"的路由收益**。如果收益只出现在跨数据集的混合中，在单个数据集内部消失，那就和 QASPER 的结论一致，而且这本身就可以写进论文。
4. 优先级：MuSiQue > HotpotQA（混合语料）> NQ（作为 QASPER 结论的推广检验）> 2Wiki > TriviaQA ≈ SQuAD。
5. 所有付费运行都要单独批准，在非高峰时段（UTC 01–04、06–10 以外）进行；test 集仍然只在最后用一次。
